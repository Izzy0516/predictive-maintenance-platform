## What this project is

I built a small machine learning system that predicts how many operational cycles a jet engine has left before it fails, based on its sensor readings. The pipeline is written in Python, the model is served through a FastAPI endpoint, and the whole thing is tested and continuously integrated.

My best model reaches an RMSE of 17.9 on the held-out `test_FD001` set, which sits inside the published benchmark range for this dataset.

## Why I chose this problem

I'm studying Motorsport Engineering, and Remaining Useful Life prediction is exactly the kind of problem that sits behind component life management in real motorsport: gearbox change rules in F1, ERS component lifetimes, power unit life budgets. It's also the same problem industrial predictive maintenance solves at scale. The technical shape of the task, sensor time series turned into a regression problem, is a compact way to demonstrate the full ML engineering cycle: data cleaning, feature engineering, model selection, honest evaluation, serving, and testing.

I wanted to build something end to end, not just a notebook, and I wanted every decision in it to be one I could defend.

## Results

I trained four models and evaluated them on the untouched `test_FD001.txt` file (100 engines, one prediction per engine at the last recorded cycle):

| Model | RMSE | NASA score |
|---|---|---|
| Mean baseline | 41.94 | 33,354 |
| Ridge regression | 21.03 | 1,337 |
| Random Forest | 18.26 | 1,149 |
| **HistGradientBoosting** | **17.93** | **865** |

Gradient boosting's RMSE of 17.93 is close to the Saxena et al. (2008) benchmark of 18.4 on this dataset. I also ran 5-fold engine-grouped cross-validation on the training set to check that the numbers were stable, and they were (see `notebooks/02_baseline_model.ipynb`).

One thing worth flagging: the rank ordering on the NASA score isn't the same as it was in cross-validation. Ridge won on NASA score during CV, because tree ensembles' tendency to average pulled their near-failure predictions toward the middle, which the NASA score punishes exponentially. On the held-out test set, most engines are still relatively healthy at their final recorded cycle, so gradient boosting comes out ahead on both metrics. Which model is "best" depends on what regime you're operating in.

## Method: the decisions worth defending

Three technical choices shape everything downstream. Each of them is enforced by a test, so it can't be silently broken later.

**1. RUL clipping at 125 cycles.** Remaining Useful Life can't be measured directly, so I reconstructed it from run-to-failure data. But if I use raw RUL as the target, the model is being asked to distinguish a healthy engine with 190 cycles left from a healthy engine with 210 cycles left, and the sensors just don't support that. The degradation hasn't started yet. Following Heimes (2008), I clip the target at 125, which is equivalent to saying "engines are healthy until they have 125 cycles left, then they start degrading linearly." The evidence backs this up: Pearson correlations between the sensors and RUL are 4 to 5 times stronger in the degraded region than in the healthy region.

**2. Engine-grouped train/test splits.** Rows within one engine are highly correlated. Cycle 87 and cycle 88 of the same engine are almost identical readings. If I use `train_test_split` naively, roughly 20% of every engine's rows land in the test set, and I end up with a fake RMSE of around 12 to 14, because the model has effectively seen a near-identical copy of every test row during training. `GroupKFold` on `engine_id` fixes this by mirroring the real deployment situation: the model is evaluated on engines it has never seen.

**3. Two metrics, always reported together.** RMSE is symmetric, but late predictions aren't as forgivable as early ones in this domain. The NASA C-MAPSS scoring function penalises late predictions (predicted RUL greater than true RUL) exponentially with a denominator of 10, and early predictions with a denominator of 13. So a 30 cycle late error costs about 19.09 on the NASA scale, while a 30 cycle early error costs about 9.05. Late errors are roughly twice as expensive as early ones, which reflects the real world cost of missing an imminent failure. If I only reported RMSE, I'd be hiding the failure mode I care most about.

The full reasoning behind each of these choices, with supporting numbers, is in [`PROJECT_GUIDE.md`](PROJECT_GUIDE.md).

## The API

A FastAPI service exposes the trained model over HTTP. You send it a JSON payload with sensor readings, and it sends back a predicted RUL and a maintenance recommendation:

```
POST /predict
{
  "features": {
    "s2": 642.15,
    "s3": 1591.82,
    ...
  }
}

→
{
  "predicted_rul": 34.2,
  "recommendation": "schedule_inspection"
}
```

There's also `GET /health` for a liveness check, and interactive OpenAPI docs at `/docs` when the service is running. Input validation is handled by Pydantic; if a caller forgets a required feature, they get an HTTP 400 with a clear message rather than a silent failure. The recommendation layer (`healthy`, `schedule_inspection`, `immediate_inspection`) is a small business logic layer that converts the raw number into an action.

## Testing

There are 39 tests, all passing. I wrote them to pin down the design decisions I made, not just to check that the code runs:

* **Metrics.** Perfect predictions score 0. RMSE is symmetric in sign. NASA score is asymmetric (late errors cost more than early ones). NASA aggregates by sum, not mean.
* **Data pipeline.** RUL is 0 at the last cycle of each engine. Clipping caps the healthy region correctly. Rolling windows never bleed across engines. No NaN rows appear after feature engineering, thanks to `min_periods=1`.
* **Splits.** No engine appears in both the train and test side of any fold. Every row shows up in exactly one test fold. The splitter fails loudly on bad input rather than silently doing the wrong thing.
* **Models.** The baseline's RMSE equals the standard deviation of the target (this is a mathematical identity, and it's a nice cross-check). Ridge beats the baseline on data with any linear signal. The Ridge pipeline includes the scaler step. Gradient boosting beats the baseline.
* **API.** `/health` returns 200. `/predict` returns the expected shape. Missing features give a 400. A malformed body gives a 422. The recommendation is always consistent with the predicted RUL.

Run them with `pytest -v`.

## Running it locally

```bash
# 1. Set up
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Get the data
# Download CMaps.zip from
#   https://www.kaggle.com/datasets/behrad3d/nasa-cmaps
# Unzip and place train_FD001.txt, test_FD001.txt, RUL_FD001.txt
# into data/raw/

# 3. Run tests
pytest -v

# 4. Train and persist the model
python -m src.train

# 5. Start the API
uvicorn src.api:app --reload

# 6. In your browser
# http://127.0.0.1:8000/docs   for the interactive API docs
# http://127.0.0.1:8000/health for the liveness check
```

## What I deliberately left out

I want to be honest about scope, because a portfolio project is stronger when it's clear about what it isn't.

* **No frontend.** I originally planned a React dashboard, then cut it. It would have been architecture theatre for a project where nothing needs to persist between requests. The `/docs` page is already a fully interactive interface to the model.
* **No database.** The trained model lives in a file on disk. Adding Postgres to a stateless prediction service would be complexity without any real value.
* **Not fine-tuned to state-of-the-art.** My goal was to hit the published FD001 benchmark range with defensible methodology, not to beat it. Beating the benchmark takes deep learning and months of tuning. Matching it, with clean engineering around it, demonstrates the skills I actually wanted to show.
* **FD001 only.** FD002 through FD004 add multiple operating conditions and would need condition-normalisation preprocessing. That's real follow-up work, but it was out of scope for a single-dataset baseline.
